## 0. 一句话结论

**这不是一个新方案，而是我们 `index.html` 里那套「ESP32 + PCA9685 + 5×SG90 腱绳手」的现成第 0 号原型**：
BOM 逐项对得上，而且它把结构件、接线说明、BLE 固件、11 个手势预设置全部补齐了 —— 正好压中
`docs/ORCA-自主架构-PWM方案.md` §7「下一步 1：买 1 个舵机 + 1 个 PCA9685 实测」那条。

但固件的**归一化层有一个五指语义不一致的 bug**（§5.1），上电/断线/速度三处行为也不适合当从端。
可用结论：**抄结构与软件架构，固件要修，链路要换。**

### 1.2 接线文档里的硬信息（固件注释里没有的）

- 舵机 `SG90`（塑料齿、1.6–2.2 kg·cm、5V）：棕=GND / 红=5V / 黄=PWM
- `PCA9685.VCC → ESP32-C3 3.3V`，`GND` 共地，`SDA→GPIO8`，`SCL→GPIO9`，**`OE → GND`（输出常开）**，
  `V+ →` 外接 5V 正极（**明确写了不能接 ESP32 任何引脚**）
- PCA9685 上下两排 6 针互通；竖列从板边起 0–7…，五指用前五路

⚠️ GPIO9 是 ESP32-C3 的 **BOOT 拉脚**（低电平进下载模式）。I2C 上拉会把它拉高，所以能正常启动；
但如果沿用了「强下拉」或接了按下即接地的按键，**上电会进下载模式**。接线文档没提这一条。

### 1.3 固件做了什么

```
BLE(设备名 xiaochu)  写特征 39dea685-…  service 89d60870-…
  ├─ "servo_<i>=<角度>"   → Finger::setTargetAngle()      直接 0–180
  └─ 其它字符串           → HandMovementFactory::applyGesture()
                             fist/five/ok/rock/love/one/two/three/four/scratch/come 共 11 个
loop(10 ms): 每个手指 currentPosition 以 2°/步 线性逼近 target → PCA9685 写 PWM
```

每指有一张「位姿标定表」：`MAX_OPEN` / `MAX_CLOSED` / `direction`，共 10 个常量。
`SERVO_MIN/MAX_PULSE = 150/500`，50 Hz，振荡器 27 MHz（与 Adafruit 官方示例一致，✅ 初始化顺序正确）。

| 环节 | 我们（`index.html` / `淘宝3D打印交付包.md`） | 小楚君 | 差异 |

## 3. 值得直接抄的三样

1. **Finger/Hand 两层的插值结构**：`currentPosition → target`，每 10 ms 逼近一步。
   和 `app.js` 的 One Euro 滤波器互补（视觉侧平滑 + 执行侧限速），分层是对的。速度参数见 §5.3。
2. **每指 `MAX_OPEN` / `MAX_CLOSED` 标定表**：这正是我们缺的 `flex(0–100) → PWM 角度` 映射常量，
   而且**应该和 ORCA 的关节 ROM 夹取一样留在设备/适配层**，不要进 `app.js`。
3. **双层指令协议**：`servo_i=angle`（连续）+ 手势名（离散）。离散那层可以顺手做成网页的「预设手势」按钮。

## 4. 接入链路：三条路线

`app.js` 现在只有一条出口：`BRIDGE_URL = http://127.0.0.1:8765/update`，payload 是
`{fingers:{thumb:{flex,mcp,pip,dip},…}, world_landmarks}`。`flex` 已经是 **0–100 的综合弯曲角**
（`min(100, (mcp+pip+dip)/2.7)`）—— 也就是说**降维这一步我们早就做完了**，5 自由度手不需要新算法。

| 路线 | 链路 | 优点 | 代价 |
|---|---|---|---|
| **A. 浏览器直连 BLE** | `capture.html` → Web Bluetooth → ESP32 | 零 Python、零配网、5 分钟能演示 | 仅 Chrome/Edge（含安卓），iOS Safari 不行；ATT MTU 默认 **20 B**，要改成二进制帧 |
| **B. ESP32 自建 HTTP** | `capture.html` → `POST http://<esp32>/update` | **payload 与 `bridge_server.py` 完全同构，`app.js` 只改一行 URL**；任意浏览器 | ESP32 要连 WiFi + 配网；C3 单核，30 Hz + 5 路 PWM 要留意 |
| **C. 挂进 ORCA 适配层** | `orca_bridge.py --sink esp32` | 复用现成的 17→5 降维、限速、ROM 夹取、`--sink` 抽象 | 只为了让 ORCA 生态也能驱动它，平时不划算 |

**推荐顺序：A →（要交付/跨端时）B → 真需要时再 C。**
`--sink` 已经是 `choices=["print","orca","grpc"]`，将来加 `esp32` 是自然扩展，不是重构。

### 4.1 协议改造建议（两条都很小）

**A 路线的二进制帧**（绕开 20 B MTU）：

```
[0xA5, thumb, index, middle, ring, pinky]   // 6 字节，每字节 0–180 直接就是角度
```

`PROPERTY_WRITE_NR`（无响应写）固件已经开了，30 Hz 一帧 6 字节毫无压力。

**B 路线的 payload 同构**：直接收 `{"fingers":{"thumb":{"flex":42},…}}`，
**由固件用 §3.2 的标定表把 flex 换成角度** —— 这样 `app.js` 一行都不用改，标定也留在了设备上。

### 4.2 官方上位机（`XiaochuHand.exe`）逆出来的真实协议

exe 是 **PyInstaller onefile**（PE32+，1663 个归档条目）：**Python 3.10 + Kivy GUI + bleak(BLE) + MediaPipe 0.10.35 + OpenCV + numpy 2.2.6**。
主脚本 `main`（约 1420 行）与 `gesture_controller` 模块都能从 CArchive/PYZ 里完整取出并解码常量，以下是**实证**而非猜测：

**架构与我们完全同构**：`Kivy UI → BleWorker(bleak) → BLE 写特征`，手势侧 `GestureController → MediaPipe HandLandmarker → 手势名`。

**四个 BLE 特征**（设备名默认 `xiaochu`，与固件一致）：

| 用途 | UUID | 仓库固件里有吗 |
|---|---|---|
| 写命令 | `39dea685-a63e-44b2-8819-9a202581f8fe` | ✅ 有 |
| About（读 JSON） | `b2a49d41-a2ac-48c3-b6c8-cfd05640654e` | ❌ **没有** |
| Settings（读/写 JSON 字段） | `68b788da-819b-4feb-b478-8d237ef29f5f` | ❌ **没有** |
| OTA（notify + 令牌） | `3168e56f-6ea1-420d-98f8-08a3b34afc9b` | ❌ **没有** |

**指令集**（与固件解析逻辑对齐）：

| 指令 | 方向 | 说明 |
|---|---|---|
| `servo_<idx>=<angle>`，idx 0–4，angle 0–180 | 滑块 / 自定义输入框 | **原文 docstring：「滑块范围 0~100，内部映射角度 0~180」** → 就是**原始角度直发**，不做逐指标定 |
| `five` `four` `three` `two` `one` `ok` `rock` `love` `fist` `scratch` `come` | 手势/预设按钮 | 与固件 `HandMovementFactory` 的 11 个名字**逐一对应** |
| 任意自定义字符串 | "Custom:" 输入框 | 可直接手动发任何指令（调试很方便） |

**手势识别算法**（`gesture_controller`，`get_angle` + `recognize`）：
用 MediaPipe 21 点算**每指三点夹角**（指尖 `(4,8,12,16,20)` 与 `(2,6,10,14,18)` 组合），
与阈值常量 **160°** 比较（小于 160° 视为弯曲），得到 5 位二值状态，再拼成手势名（`握拳 (Fist)` / `张开 (Open Palm)` / `拇指 + 食指 (单指)`…）。
模型参数：`hand_landmarker.task`、`num_hands=1`、`min_hand_detection_confidence=0.7`、`min_tracking_confidence=0.5`、摄像头 640×480。

> **模型文件和我们的一样**：exe 里的 `hand_landmarker.task`（7,819,105 B，sha256 `fbc2a30080c3c557…`）
> 与 `finger-motion-replay/vendor/` 下那份**逐字节相同**。两边是同一个 MediaPipe 模型、同一条视觉路线。

**OTA 流程**（说明存在一版更完整的固件）：`OTA` 按钮 → 填 Wi-Fi SSID/密码 → **经 BLE 下发给设备** →
设备自己连 Wi-Fi 起 HTTP 服务 → app 用 `POST`（带 `x-ota-token` 头）上传 `.bin/.hex/.zip` → 设备经 OTA 特征 notify 回报进度。

⚠️ **版本错配**：exe 期望 ABOUT / SETTINGS / OTA 三个特征，而仓库里的 `.ino` 一个都没实现。
所以拿仓库固件配这个 exe：**滑块、自定义、手势都可用；Settings / About / OTA 必然失败**。
反过来说 —— 我们**不需要这三个功能**，自己写 BLE 客户端时只对接写特征即可。

## 5. 固件里**不能**照抄的四处（含复算证据）

### 5.1 `direction` 双重取反：中指的归一化语义和其它三指相反 ⚠️ 最值得先验证

```cpp
if (direction == 1) target = map(pos, 0, 100, maxOpen, maxClosed);
else                target = map(pos, 0, 100, maxClosed, maxOpen);
```

`maxOpen` / `maxClosed` **本身就已经编码了方向**（中指开=180>合=0，说明合拢时角度变小）。
再按 `direction` 翻一次，就是双重取反。按固件自己的常量复算：

| 手指 | MAX_OPEN | MAX_CLOSED | dir | `pos=0` 应=开 | 实际 | `pos=100` 应=合 | 实际 |
|---|---|---|---|---|---|---|---|
| 拇指 | 30 | 180 | 1 | 30 | 30 ✅ | 180 | 180 ✅ |
| 食指 | 10 | 180 | 1 | 10 | 10 ✅ | 180 | 180 ✅ |
| **中指** | **180** | **0** | **-1** | 180 | **0 ❌** | 0 | **180 ❌** |
| 无名 | 0 | 180 | 1 | 0 | 0 ✅ | 180 | 180 ✅ |
| **小指** | **180** | **35** | **-1** | 180 | **35 ❌** | 35 | **180 ❌** |

于是手势也反了：

| 手势 | 拇指 | 食指 | 中指 | 无名 | 小指 | 现象 |
|---|---|---|---|---|---|---|
| `fist`（全握） | 180 合 | 180 合 | **180 开** | 180 合 | **180 开** | 中指小指翘着 |
| `five`（全张） | 30 开 | 10 开 | **0 合** | 0 开 | **35 合** | 中指小指蜷着 |

**为什么作者自己没发现**（已从 exe 侧证实，见 §4.2）：官方上位机的滑块走的是 `servo_i=angle`
（docstring 原话「滑块范围 0~100，内部映射角度 0~180」），**完全绕开了归一化层**，
只有手势/预设按钮会踩到归一化层 —— 也就是说这个 bug **只影响 11 个手势键**，滑动手动控制一切正常。

**30 秒台架验证**：只接一个舵机到通道 2，发 `servo_2=0` 和 `servo_2=180`，看哪个是「开」。
- 若「开」= 180° → 常量是对的，代码错了（改 §5.1 三处）
- 若「开」= 0° → `MIDDLE_MAX_OPEN` / `MIDDLE_MAX_CLOSED` 两个名字写反了，机制其实自洽

**修复**（一处根因，三处同源）：

```cpp
// 1) 映射：direction 是冗余的，open/closed 的角度谁大谁小已经说明了一切
target = constrain(map(pos, 0, 100, maxOpen, maxClosed), 0, 180);

// 2) 上电位姿：一律在「开」
currentPosition = target = maxOpen;

// 3) 启动直接写 PWM 那段：用各指自己的 maxOpen，而不是全通道 map(0)
pwm.setPWM(f.channel, 0, map(f.maxOpen, 0, 180, SERVO_MIN_PULSE, SERVO_MAX_PULSE));
```

### 5.2 上电甩手 ~0.75 s

`setup()` 里 5 路全写成 `map(0, 0, 180, …)` = 0°，**不是各指的「开」位姿**（拇指开在 30°、
中指/小指开在 180°）。之后靠 `loop()` 每 10 ms 走 2° 爬回去：180° 行程 = 90 步 = **0.9 s**，
就是开机时那一阵乱甩。按 §5.1 第 3 条改即可。

### 5.3 插值速度比 SG90 慢 2.5 倍 —— 直接造成「跟手迟滞」

| 项 | 数值 |
|---|---|
| 固件 | `DEFAULT_STEP 2.0°` / `delay(10)` → **200 °/s** |
| SG90 手册 | 0.1 s/60° → **600 °/s** |
| 拇指全行程（30→180，150°） | 固件 **750 ms**；舵机本身只要 250 ms |

而我们视觉侧 **30 Hz**（33 ms 一帧）+ One Euro 已经足够平滑，固件这层定速爬坡是**多余的减速带**。
建议 `flex → 角度` 直发、`step` 拉到 20–30°（≈ 2000 °/s，等于关闭插值），把平滑留给 One Euro；
真要做加减速就做 S 曲线，别做定速。

### 5.4 断线 / 故障行为不适合当从端

- **无超时保护**：BLE 断开后手停在最后姿态（`mc_hand.lua` 那套我们做的是「1 秒无数据判定手离开」）。
  从端至少要：500 ms 无新目标 → 回中立位 / 断 PWM。
- **`PCA9685 not found` 时 `while(1)` 死等**：I2C 一次接触不良就砖住，应该退避重试 + 报错，而不是死循环。
- **没有 OE 断电**：`OE` 被文档要求直接接地 → 舵机常开、持续保持力矩、SG90 会嗡嗡响发烫。
  PCA9685 的 OE 是**低有效**，用一根 GPIO 就能做「静止 1 s 后关输出」，对电池供电很关键。
- 其它小问题：`abs()` 用在 float 上（应 `fabs()`）；`run()` 每 10 ms 无条件重写 5 路 I2C
  （可用 `isStill()` 省掉，那个函数现在写了但没人用）；`String` 在 BLE 回调里拼接。

### 5.5 脉宽范围偏窄

`150–500` tick，50 Hz 下 1 tick = 4.883 µs → **0.73–2.44 ms**，放弃了下限约 0.23 ms。
标准舵机 0.5–2.5 ms 对应 **102–512**。加上 SG90 个体差异和 PCA9685 模块振荡器（25 vs 27 MHz）
误差，**逐通道标定是必须的**，不能指望一套常量通用——这正是第 6 节第 1 条的动机。

## 6. 三个真正的新想法

### 6.1 用视觉管线做「自动标定」，把 10 个硬编码常量变成自标定产物

现在是手调 `THUMB_MAX_OPEN=30` 这类常量。但我们的 `app.js` 已经是**角度真值源**：

```
对每一路 ch：扫 pulse → 摄像头读该指 flex → 拟合 flex(pulse)
            → 取 flex 最小时的 pulse = MAX_OPEN，最大时 = MAX_CLOSED，写回固件/配置
```

这就是 ORCA 链路里那套「28/28 映射验证」的同款做法，30 行脚本的事，
而且**顺带把 §5.5 的个体差异一起消掉**。

### 6.2 手势「自证」回归测试：让手自己验证自己

固件里那 11 个手势表可以直接当测试用例：

```
机械手摆出 "two"（伸食指中指） → 摄像头回读 MediaPipe → 判定是否被识别为 two → 通过/失败
```

这一招只有在**有实物**时才能做，而这只手 ¥80。它测的是端到端的「表观保真度」——
比任何关节角数值对比都更接近用户感知，而且能直接暴露 §5.1 那种语义 bug（摆 `fist` 却被识别成 `rock`）。

### 6.3 加第 6 路：拇指对掌/外展

PCA9685 有 16 路，现在只用 5 路。`love`（比心）和 `ok` 这类手势之所以「不像」，
缺的正是**拇指外展**——这也正好是 ORCA 17 DOF 相对于我们的核心增量（`world_landmarks` 才解得出来的那部分）。
加一路舵机做拇指对掌旋转，5→6 DOF，`love`/`ok` 立刻立体。
成本一路舵机 + 一个打印件，收益比从 5 DOF 硬凑手势大得多。

## 7. 风险与授权（**有商业化意图，必看**）

1. **仓库没有 `LICENSE`**，也没有 `.git` → 默认版权保留。我们的 `淘宝3D打印交付包.md` 是要对外交付的，
   **不能直接复印它的 STL 或固件分发**。可行做法：只借鉴结构思路，用 `gen_forearm*.py` 那套
   「板子/结构即代码」的方式**自己重画**；真要复用就先联系作者拿书面许可。
2. **而且那个 169 MB 的 exe 里明确写着第三方授权**（About 弹窗的字符串）：
   ```
   License
   Xavier Grosjean
   Creative Commons
   Attribution-NonCommercial-ShareAlike 4.0 International
   (CC BY-NC-SA 4.0) open-source license
   ```
   即它的**手势识别模块派生自 Xavier Grosjean 的项目，是 NC（禁止商用）+ SA（同协议开源）**。
   我们的交付包/淘宝路线**绝对不能**把这段代码抄进去（NC 直接冲突，SA 还会传染许可证）。
   好消息是它的算法本身很简单（三点夹角 < 160° 判弯曲），我们用现有的 One Euro 屈曲角
   自己写十几行就等价甚至更好，**不存在技术依赖**。
3. **SG90 塑料齿、1.6–2.2 kg·cm** 只适合展示/教学，不能抓取。我们 PWM 路线规划的是
   20 kg·cm 级金属齿舵机，**两者不能混进同一份 BOM**（会误导买家）。
4. **供电**：文档只写了「外接 5V」，没写电流和电容。5×SG90 同时启动瞬态 > 1 A，
   必须 5V/2 A + **共地** + ≥ 1000 µF 电解。这条我们 `servo-dist-board/README.md` 已经量化过了，直接引用即可。
5. `备份代码.txt` 与 `.ino` 内容完全相同（只差换行符），不建议一起收进我们的仓库。
